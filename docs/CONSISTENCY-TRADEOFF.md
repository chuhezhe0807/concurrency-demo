# 分布式事务选型：强一致 vs 最终一致（US-023）

承接 US-019 暴露的同一个缺口——下单跨 order/product 两个独立本地事务，本地 `@Transactional` 管不到对方，
「扣库存成功但建单失败」会留下脏数据。我们用两条**互不替代**的路径补上了它：

- **强一致**：[SEATA.md](SEATA.md)（US-021）——Seata AT 模式，全局事务协调器把两个本地事务绑成一个，要么都提交要么都回滚。
- **最终一致**：[RELIABLE-MESSAGE.md](RELIABLE-MESSAGE.md)（US-022）——本地消息表 + RabbitMQ + 消费端幂等，先落订单再异步可靠地扣库存。

本篇不重复两种方案的实现细节（见各自文档），只做**选型对比**：它们各自适合什么场景、代价在哪、复杂度多高、怎么选。

## 1. 一句话本质

| | 强一致（Seata AT） | 最终一致（可靠消息） |
| --- | --- | --- |
| 核心承诺 | **同一时刻**所有服务的数据一致：调用返回即一致 | **某个时刻之后**一致：返回时还不一致，过一会儿对齐 |
| 实现思路 | 2PC：协调器统一提交/回滚，过程对外尽量不可见 | 解耦：先保证消息不丢，靠重试/补偿把状态推到最终一致 |
| 一句话 | 「要么都成功，要么都回滚，当场见分晓」 | 「先把能做的做了，剩下的保证迟早做完」 |

## 2. 核心对比

| 维度 | 强一致（Seata AT，US-021） | 最终一致（可靠消息，US-022） |
| --- | --- | --- |
| **一致时点** | 同步、即时。`POST /orders` 返回时库存已扣、订单已建 | 异步、有窗口。返回时订单 `待确认(0)`，~1.5s 后才 `已确认(1)`/`已取消(2)` |
| **下游可用性要求** | **下游必须在线**。product-service 挂了 / Feign 超时 → 全局回滚，下单失败 | **下游可短暂不可用**。消息堆在队列里，product 恢复后继续消费，下单不受影响 |
| **吞吐 / 延迟** | 较低。同步等待整条链路 + 全局锁串行化热点行 | 较高。下单只写本地库即返回（实测 `elapsedMs≈146`），扣库存异步并行 |
| **耦合度** | 紧。调用方编排、等待被调方结果 | 松。两服务只通过消息契约耦合，可独立伸缩/部署 |
| **失败处理** | 自动回滚（undo_log 前镜像还原），业务无感 | 业务级补偿：库存不足 → 订单改 `已取消`；需自己设计补偿语义 |
| **并发控制** | 全局锁防脏写，热点行上是竞争点 | 无全局锁；超卖兜底靠扣减时 `stock >= quantity` 乐观判断 |
| **运维依赖** | 多一个 **TC（Seata Server, 8091）**，单点/集群、存储模式要管 | 多一个 **消息中间件（RabbitMQ, 5672）**，要管队列/DLX/堆积/重复 |
| **业务侵入** | 低：`@GlobalTransactional` + 数据源代理，业务 SQL 不变 | 中：要写本地消息表、轮询投递器、幂等去重表、结果回传监听 |
| **数据可见性** | 默认读未提交：能读到一阶段已提交但全局未决的中间值（严格需 `@GlobalLock`+`for update`） | 天然存在「订单已建、库存未扣」的中间态，业务需接受并展示「待确认」 |

## 3. 性能代价对比（为什么强一致更慢）

强一致的代价集中在**同步阻塞 + 全局锁**：

```
强一致：POST ──▶ [扣库存(等)] ──▶ [建单(等)] ──▶ TC 全局提交(等) ──▶ 返回
        └────────── 全程同步，热点行被全局锁串行化 ──────────┘   ← 用户等到这里

最终一致：POST ──▶ [写 t_order + t_outbox 本地事务] ──▶ 立即返回(~146ms)
                                                          ⋮ 异步
          OutboxRelay 投递 ─▶ MQ ─▶ 扣库存 ─▶ 回传 ─▶ 订单确认  ← 用户早已拿到响应
```

- **强一致**把「扣库存 + 建单 + 协调提交」全压在请求线程里同步等；热点商品（同一行被高频扣减）上，AT 全局锁会让并发全局事务在该行排队，吞吐随热点竞争下降。这正是 US-020 热点扩容要面对的痛点在强一致下被放大。
- **最终一致**把链路砍成「本地写库即返回」+「异步扣库存」两段。用户感知延迟只到第一段；第二段的吞吐由消费者并发 + 横向扩容决定，且无全局锁。代价是引入了「待确认」窗口。

## 4. 复杂度对比（哪种更难落地）

两者复杂度落在**不同位置**：

- **强一致**：实现简单（加注解、配数据源代理），**心智复杂度低**——业务代码几乎和单体一样。复杂度被 Seata 和 TC 吃掉了，代价转移到**运维与故障域**：TC 单点/选型、`undo_log`、全局锁死锁、读隔离语义、版本对齐（client/server 都得 2.1.0）。
- **最终一致**：运维相对熟悉（就是个 MQ），但**应用代码复杂度高**——双写缺口要本地消息表兜、重复投递要幂等表兜、在途投递要护栏（见 RELIABLE-MESSAGE.md 第 6 节）、毒消息要 DLQ、补偿语义要自己设计、订单要多出「待确认/已取消」状态机。**正确性责任在业务侧**。

> 一句话：强一致是「框架替你扛复杂度，但你被框架和 TC 绑住」；最终一致是「基础设施轻，但每一处不丢/不重/补偿都得你自己写对」。

## 5. 选型建议

按**业务能不能接受「中间不一致窗口」**这一条来切，是最快的决策线：

```
能接受「下单后短暂看到待确认、库存稍后才扣」吗？
├─ 不能（必须当场强一致、对账要求严苛）           → 强一致 / Seata
│   典型：账户转账、扣款与发货必须原子、金融对账、库存即下单即锁定
└─ 能（最终对齐即可，要高吞吐/高可用/服务解耦）   → 最终一致 / 可靠消息
    典型：电商下单扣库存、积分发放、通知/履约、跨服务数据同步
```

更细的权衡：

- **选强一致（Seata）当**：操作天然要求原子且同步可见；下游高可用、不允许「先答应后取消」；并发不高、热点行竞争可控；团队更愿在运维侧投入而非业务侧写一堆兜底。
- **选最终一致（可靠消息）当**：要高吞吐、要削峰、要服务解耦与独立伸缩；能接受秒级不一致窗口和「待确认 → 确认/取消」语义；下游可能短暂抖动但最终会恢复。
- **可以混用**：同一系统里按业务分级——强一致用于资金/库存锁定等关键路径，最终一致用于通知/积分/履约等可补偿路径。不必全局二选一。

## 6. 各自局限（汇总）

**强一致 / Seata AT**（详见 SEATA.md 第 5 节）：
- 只适合**关系型库**且 SQL 能被 Seata 解析。
- **全局锁**在高并发热点行上成为竞争点，吞吐受限。
- 默认**读未提交**，严格读已提交需 `@GlobalLock` + `for update`。
- TC `STORE_MODE=file` 是单点、重启丢未决事务；生产需 `db`/`raft` 存储 + TC 集群。
- 下游不可用会直接导致下单失败（强同步依赖）。

**最终一致 / 可靠消息**（详见 RELIABLE-MESSAGE.md 第 6 节）：
- **最终一致而非强一致**：存在「订单待确认」窗口，超卖兜底靠扣减时乐观判断而非下单时锁定。
- **补偿要自己设计**：本演示「不足就不扣」无需冲正；若改「先预扣再确认」，取消时要发反向消息加回库存（TCC/Saga 补偿），复杂度上升。
- **至少一次投递**：靠消费端幂等去重保证只扣一次；幂等表 `t_stock_deduct_log` 会无界增长，需归档。
- 毒消息进 DLQ 后**无自动告警/消费**，依赖人工排查补偿。

## 7. 实测数据对照（同一请求 `{userId:1, productId:7, quantity:3}`）

| | 强一致（SEATA.md §4） | 最终一致（RELIABLE-MESSAGE.md §5） |
| --- | --- | --- |
| 成功路径 | HTTP 200，返回时 stock 已 -3、订单已落库（即时一致） | 立即返回 `elapsedMs≈146`，订单 `status=0`；~1.5s 后 `status=1`，stock -3 |
| 失败/补偿路径 | `mockFail=true` → HTTP 500，**全局回滚**：stock 不变、订单不落库 | 超库存 `qty=2000000` → 先返回 `status=0`，~1s 后 `status=2` 已取消，stock 不变 |
| 重复请求 | 全局事务内一次性提交，无重复语义 | 重投消息 → 幂等跳过，stock 不重复扣，订单已终态忽略 |
| 失败时的数据归位 | undo_log 自动还原（框架） | 业务补偿改订单状态（应用代码） |

两条路径都正确补上了 US-019 的缺口，区别只在**何时一致**与**代价落在哪**——这正是分布式事务「没有银弹、只有取舍」的体现。
